# Local Asset Library Agent Access Plan

Date: 2026-06-17

## Recommendation

Use a local or external-drive asset library as the low-cost first implementation for Marketing OS asset access.

This keeps original product photos, logos, videos, and working files on hardware we control, while giving the agent a predictable index of assets it can search and reference. It avoids adding a $99/month DAM subscription before the business has proven that a managed DAM is worth the recurring cost.

The first version should not try to recreate a full DAM. It should be a simple, disciplined file library plus a local metadata index.

## Goal

Give Marketing OS and Codex access to product photos, company logos, source videos, generated assets, and brand files without storing them inside the code repository.

The integration should answer:

- What assets exist?
- Which product, campaign, or channel does each asset belong to?
- Which assets are approved for use?
- Where is the file located on disk?
- What are the dimensions, file type, and useful preview metadata?
- Which assets are missing, stale, duplicated, or unmapped?

## Suggested Storage Model

Use an external drive mounted on the agent computer, with a stable mount path.

Preferred path on macOS:

```text
/Volumes/MarketingAssets
```

If the drive name changes, the integration will break, so the drive should have a stable name and stay mounted before running Marketing OS asset workflows.

Recommended top-level structure:

```text
/Volumes/MarketingAssets/
├── brand/
│   ├── logos/
│   ├── colors/
│   └── guidelines/
├── products/
│   └── product-slug/
│       ├── source/
│       ├── edited/
│       ├── listing/
│       └── generated/
├── campaigns/
│   └── campaign-slug/
│       ├── source/
│       ├── working/
│       └── final/
├── videos/
│   ├── source/
│   ├── clips/
│   └── final/
├── templates/
│   ├── graphics/
│   └── video/
└── _index/
    ├── assets.sqlite
    ├── assets-manifest.json
    └── thumbnails/
```

The `_index` folder is generated or maintained by Marketing OS. The rest is human-readable storage.

## Metadata Strategy

Use a local SQLite index for the app and agent, plus optional sidecar files for portability.

SQLite table fields:

- `asset_id`: stable local ID generated by Marketing OS
- `path`: absolute file path
- `relative_path`: path relative to `/Volumes/MarketingAssets`
- `filename`
- `sha256`: content hash for duplicate detection
- `size_bytes`
- `mime_type`
- `asset_type`: image, video, audio, document, logo, design, generated
- `width`
- `height`
- `duration_seconds`
- `product_slug`
- `campaign`
- `asset_role`: product_photo, logo, lifestyle, packaging, process, video, template, generated_output
- `asset_status`: approved, draft, needs_review, archived
- `platform_fit`: instagram_feed, instagram_reel, facebook, etsy, website, email
- `rights`: owned, licensed, restricted, unknown
- `brand_safe`: yes, no, review
- `created_at`
- `modified_at`
- `indexed_at`
- `thumbnail_path`
- `notes`

Optional sidecar files can live next to important assets:

```text
photo-name.jpg
photo-name.asset.json
```

Sidecars are useful for portability, but the first version can rely on SQLite plus path conventions.

## Agent Access Pattern

The agent should not browse the whole drive blindly during normal planning. Instead:

1. Marketing OS scans the asset root and updates the index.
2. The agent queries the index for relevant assets.
3. The app shows thumbnail previews from `_index/thumbnails`.
4. The agent only opens original files when needed for generation, inspection, or export.

This keeps workflows fast and prevents the agent from wasting time crawling large video/photo folders.

## First Implementation Shape

Add a local asset adapter:

```text
marketing_os/integrations/local_assets.py
```

Suggested methods:

```text
scan_asset_root(root_path)
search_assets(query=None, product_slug=None, asset_type=None, asset_status=None, platform_fit=None)
get_asset(asset_id)
get_assets_for_product(product_slug)
get_brand_assets(asset_role=None)
get_thumbnail(asset_id)
mark_asset_status(asset_id, status)
set_asset_metadata(asset_id, metadata)
```

Add local config:

```text
MARKETING_OS_ASSET_ROOT=/Volumes/MarketingAssets
MARKETING_OS_ASSET_INDEX=/Volumes/MarketingAssets/_index/assets.sqlite
```

Keep these in `.env`, with blank examples in `.env.example`.

## Thumbnail And Preview Handling

Generate lightweight local thumbnails into:

```text
/Volumes/MarketingAssets/_index/thumbnails/
```

Suggested thumbnail rules:

- Images: generate JPEG or WebP thumbnail, max 600px wide.
- Videos: generate one poster frame, max 600px wide.
- PDFs/documents: generate first-page preview only if tools are available.
- Logos/SVGs: keep source path and generate PNG preview if practical.

Original files should stay untouched.

## Human Workflow

The file library should be easy for a human to manage without opening Marketing OS.

Recommended habits:

- Put every product’s source photos under `products/product-slug/source/`.
- Put edited or cleaned-up versions under `products/product-slug/edited/`.
- Put platform-ready listing images under `products/product-slug/listing/`.
- Put AI or template outputs under `products/product-slug/generated/`.
- Use `asset_status=approved` before a file becomes eligible for automatic use.
- Archive old files by status, not by deleting them.

## Benefits

- No monthly DAM cost.
- Original assets stay under local control.
- Fast access for the agent computer.
- Works offline.
- Simple backup model.
- Easy to add now without waiting for vendor API details.
- Can later migrate to Razuna, S3, Google Drive, Dropbox, or another DAM because the app has a clean asset adapter boundary.

## Tradeoffs

| Tradeoff | Impact | Mitigation |
| --- | --- | --- |
| No web access when away from the agent computer | Remote workflows cannot access assets | Add cloud sync or DAM later if needed. |
| External drive can be unplugged | Asset workflows fail | Add Data Health check for missing asset root. |
| No built-in permissions | Anyone with drive access can see files | Use OS-level disk/user permissions and keep sensitive files separate. |
| Backups are our responsibility | Drive failure could lose assets | Use Time Machine, Backblaze, or another backup target. |
| Search depends on our metadata quality | Poor metadata hurts asset discovery | Use folder conventions plus required fields for approved assets. |
| Not a collaboration portal | Contractors cannot self-serve easily | Export/share only approved subsets, or revisit DAM later. |

## Backup Requirements

This path is only sensible if backups are boring and automatic.

Minimum backup plan:

- External asset drive backed up by Time Machine or Backblaze.
- Weekly verification that backup is running.
- Optional second external drive for periodic clone.
- Never keep the only copy of product photos on a single portable drive.

## Data Health Checks

Marketing OS should warn when:

- `MARKETING_OS_ASSET_ROOT` is missing.
- The asset index is stale.
- A product has no approved image.
- An approved image file path no longer exists.
- Duplicate files are detected by hash.
- A generated output has no source asset reference.
- A large batch of files has never been indexed.
- Backup status is unknown, if we later add a backup monitor.

## Migration Path To DAM Later

This local plan should not box us in.

Keep the same source-agnostic asset fields used in the Razuna review:

- `external_source`
- `external_id`
- `external_url`
- `asset_type`
- `asset_status`
- `product_slug`
- `campaign`
- `rights`
- `last_synced_at`

For local assets:

```text
external_source=local
external_id=<local asset_id>
external_url=<absolute file path or file URI only inside trusted local UI>
```

If Razuna or another DAM becomes worth the cost later, we can upload approved assets, store returned remote IDs, and gradually switch `external_source` from `local` to `razuna`.

## Decision

For the current business stage, a local external-drive asset library is the better first step than a $99/month DAM subscription.

Build the Marketing OS asset layer around a clean adapter and metadata index. Use the external drive as the first backend. Revisit Razuna or another DAM once the asset workflow is clearly saving enough time, enabling collaboration we cannot do locally, or creating enough revenue support to justify the recurring cost.
